InsureFlow — Insurance Operations Portfolio

A full-stack insurance back-office workspace: a React and TypeScript single-page app backed by a Spring Boot REST API and a relational database. It covers customers, policies, application processing and renewal tracking behind a sign-in. It is an independent portfolio project that runs on synthetic data, and is not an official product of any insurer.

Architecture

how it fits together

Frontend

A Vite-built React 18 and TypeScript single-page app with page-level navigation (Overview, Customers, Applications, Policies, Renewals), modal forms, search, and loading, empty and error states. API calls go through one request helper that attaches the session credentials. The API base URL is configurable with VITE_API_URL.

Backend

A Spring Boot 3.5 application on Java 21, organised by feature package (customer, policy, application, security, config, health). Controllers use request records with Bean Validation, and return 404, 409 and 400 with meaningful messages through ResponseStatusException.

Database

Three tables managed by Hibernate (ddl-auto=update). Customer emails and policy numbers have unique constraints. Applications and policies currently reference people by name rather than by foreign key to customers; linking them by ID is on the roadmap.

TableColumns
customersid (PK), full_name, email (unique), phone, status, created_at
insurance_policyid (PK), policy_number (unique), holder, product, status, annual_premium, start_date, expiry_date
insurance_applicationid (PK), applicant_name, product, status, premium, submitted_at

Resource-oriented JSON endpoints under /api. Everything except the health check requires authentication.

Security approach

and its limits
  • All API endpoints except /api/health require authentication; a test asserts that an unauthenticated request returns 401.
  • Credentials come from environment variables (INSUREFLOW_SECURITY_USERNAME, INSUREFLOW_SECURITY_PASSWORD) and are held as a BCrypt hash. No secrets are stored in frontend code.
  • CORS uses an explicit origin allowlist, the H2 console is denied, and framing is blocked.
  • Bean Validation and server-side checks reject invalid input; the database enforces unique emails and policy numbers.
Honest limits. This is demonstration-grade security: one in-memory admin user, no per-user roles, no rate limiting or audit trail, and Basic credentials kept in browser sessionStorage. A real deployment needs HTTPS, an identity provider, role-based access control, and a security review. The repository's local-development default credentials must be overridden before the app is exposed publicly.

Testing and CI

quality
  • 5 backend tests with JUnit 5, Spring Boot Test, MockMvc and Spring Security Test, covering customer create and list, the authentication requirement, policy create and list, application status updates, and the health payload.
  • A GitHub Actions workflow runs the backend tests and the frontend production build on every push and pull request.
  • Not yet covered: frontend unit or end-to-end tests, update and delete paths, and validation edge cases.

Deployment and demo access

Demo access: because the app has a single admin account, I do not publish shared credentials. Instead, request a demo by email and I will walk you through it live or share a temporary environment that contains only synthetic data.

Run it locally

# backend (Java 21, Maven 3.9+)
cd backend
export INSUREFLOW_SECURITY_USERNAME='choose-a-user'
export INSUREFLOW_SECURITY_PASSWORD='choose-a-long-unique-password'
mvn spring-boot:run

# frontend (Node 20+), in a second terminal
cd frontend
npm install
npm run dev

Then open http://localhost:5173 and sign in with the credentials you chose. Full setup, including the Docker Compose stack, is in the README.
